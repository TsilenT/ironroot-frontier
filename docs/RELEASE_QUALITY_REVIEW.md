# Release quality and Steam desktop review

Reviewed 2026-11-11 against main `6544938` (v0.40.1). This review covers reliability, persistence, accessibility, performance and desktop delivery. It does not certify a Steam build, hardware compatibility or human playtest quality.

## Current foundation

- The engine has versioned identities, strict battle decoding and deterministic continuation tests. Profile sessions fence stale writers; backup replacement validates all domains and handles partial failure. Keep these protections when adding native storage.
- `dist/app.js` uses periodic autosaves, pause checkpoints, save ownership checks, visible failure messages, recovery holds, explicit restart confirmation and visibility/page-departure interruption. History and preferences retain retry paths. A renderer crash can still lose progress since the last successful checkpoint.
- The Electron shell uses a stable custom origin and persistent partition, a single-instance lock, sandboxing, context isolation and restricted navigation/network access. The shell has no general filesystem/Node bridge. This follows the direction of [Electron's security checklist](https://www.electronjs.org/docs/latest/tutorial/security); contract tests are not a security audit.
- Keyboard rebinding, pause-menu focus handling, reduced motion, audio toggles, visual objective alerts and an experimental controller adapter already exist. These are useful foundations; the canvas battlefield and physical device experience still require accessibility playtests.
- Main CI runs Node tests, syntax and runtime asset checks. It does not install/run Playwright or build native packages. Browser harness validation and browser execution are distinct checks.

## Focused change in this branch

A visible window could lose focus while combat continued: `visibilitychange` paused hidden pages, but the `blur` listener only retired input. The listener now requests the existing `pause(true)` path for an active, unpaused battle. That path saves through current ownership/recovery protection, opens the existing pause menu and requires explicit Resume. Dialog interruption behavior remains in place. Title/results and already-paused sessions do not request another pause.

Reproducible checks are in `tests/focus-loss.test.mjs` and `qa/browser/focus-loss.spec.mjs`. The browser checks transfer focus to a real child document, observing trusted blur with `document.hidden === false`; they cover checkpoint/reload, explicit Resume, interrupted Options/Guide and quota failure. This demonstrates the browser event path, not OS Alt-Tab, native dialog, Steam overlay or Deck sleep behavior. The existing middle-drag regression now explicitly resumes after blur.

The broader checks also exposed stale QA expectations on the reviewed base: flight/shared-crossing fixture validators still expected protocol 30, Shared Crossing's global catalog expected 37 missions/111 stars/10 chapter groups, and the pause focus test assumed Resume preceded every other control. Expectations now reflect protocol 31, 42 missions/126 stars/11 chapter groups and the existing Citadel upgrades control before Resume. Historical battle identities, fixture bytes and game rules are unchanged.

Before public deployment, integration must update the public build/offline cache version together with the other accepted polish changes. This focused draft does not reserve a release number or alter save protocols.

Validation: the full Node suite passed 3,510 tests with one optional desktop-tooling skip. Game syntax, runtime asset validation and the complete browser-harness check passed. The selected desktop mouse/keyboard/pause/focus set has 52 passing cases and one touch-only skip after the stale focus assertion was repaired; that assertion passed separately on all four viewport profiles. The four new focus-loss cases also passed on all three mobile viewport profiles (12 additional cases). Chromium used `/usr/bin/chromium`; these are emulated viewport/input tests, not physical-device certification. Generated logs, traces and screenshots remain under `/tmp`, outside the repository.

## Authoritative reference points

- [Steam build/store review](https://partner.steamgames.com/doc/store/review_process): the submitted near-final build must launch on every advertised operating system and implement advertised features. A passing local web build is insufficient evidence.
- [Steam Cloud](https://partner.steamgames.com/doc/features/cloud): account-specific save paths, cross-platform rules and testing must be designed explicitly; avoid synchronizing machine-specific video settings. Cloud is an optional feature, not a prerequisite for publishing on Steam.
- [Steam hardware compatibility checklist](https://partner.steamgames.com/doc/steamhardware/compat): Deck verification currently requires complete default controller access, appropriate glyphs/text entry, readable text and a playable default configuration. The documented Deck target is 30fps at 800p; interface characters must be at least 9px high at 1280x800, with 12px recommended. These are verification criteria, not general Steam store admission rules.
- [Steam hardware recommendations](https://partner.steamgames.com/doc/steamhardware/recommendations): use hardware testing to address handheld comfort and efficiency beyond the minimum checklist.
- [Steam overlay](https://partner.steamgames.com/doc/features/overlay): verify integration in the real Steam runtime. A window-blur fix alone does not prove overlay callbacks or focus behavior.
- [Game Accessibility Guidelines, Basic](https://gameaccessibilityguidelines.com/basic/): start with remapping, readable text, contrast, information beyond fixed colors/audio, saved settings and access through the same input method. These guide product quality rather than certify universal accessibility.

## Order of work

First close focused interruption defects and establish browser/package smoke checks. Next choose the native save/backup boundary and account-isolation plan; Cloud builds on that. Then test a packaged vertical slice on the supported desktop OSes and actual Deck/controllers, measure performance and repair demonstrated gaps. Finish store claims and release validation against that exact build. Keep spell/Volley rework separate throughout.
