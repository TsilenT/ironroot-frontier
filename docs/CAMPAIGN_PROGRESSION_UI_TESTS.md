# Campaign progression UI regression evidence

## Scope

`tests/campaign-progression-ui.test.mjs` executes the production function bodies from `dist/app.js` with the production campaign, engine, catalogue, scouting, objective, persistence and backup modules. It does not substitute old campaign exports for the current UI contract.

The fixture reads the actual HTML hierarchy. It implements only the DOM operations these functions need: children, class lists, IDs, simple selectors, generated buttons and click callbacks. Field-guide and scouting assertions inspect the markup generated by the actual application functions. The existing mobile geometry fixture remains separate from native layout evidence.

## Covered behavior

1. A fresh profile selects Roadside Watch, displays the 19-mission/57-star campaign, previews exactly two available buildings and starts the two-building immutable battle roster. The actual field-guide population must succeed with only warrior/archer definitions. The legacy intro is not shown for an empty profile.
2. Selecting a locked mission disables Start; calling its handler directly still cannot launch. Invoking the hidden expansion handler cannot expose unavailable definitions. Both UI selection and engine commands refuse each unavailable building without charging or mutating the battle.
3. Real result, progress persistence and Continue handlers advance through Roadside Watch, Shield at the Fork, Open Three Roads and revision-two Emberwatch. Deck and field-guide rosters progress from 2 to 5 to 8. One-star wins suffice. Repeated finish calls do not duplicate results.
4. Result markup lists only newly earned buildings. A replay does not claim the same buildings were earned again. Existing stars survive.
5. The actual Resume button decodes a saved two-building battle against a profile with newer unlocks. Resume keeps its exact old rules/state and two-card deck. A deliberate replay adopts the earned eight-building roster.
6. Returning main-campaign progress retains all eight buildings. Legacy-intro-only records retain their stars, but the new campaign still begins with Roadside Watch and two buildings. Restored revision-one Emberwatch retry/replay stays revision one with its original seven-building roster.
7. Briefing roster text, field-guide markup and scouting match the selected launch mission. Scouting with a contradictory ruleset fails instead of drawing a plausible wrong deployment.
8. Ordinary export preserves the actual scenario revision and immutable saved roster. The normal export handler refuses malformed, future, unknown/orphaned campaign data, denied reads and invalid in-memory battles. Failure neither replaces stored bytes nor reports a successful download.
9. A deterministic paid test player wins all three opening battles using the actual card-click, placement, selection and upgrade handlers. Each successful command is checked for its real gold deduction. Decisions begin at 10 seconds and occur every 5 seconds using the shared reference policy. Each battle is exported and exactly restored at 30 seconds, completes through real tick-by-tick objective evaluation, then proceeds through the actual result and Continue handlers. No gold, damage, units or simulation time is injected in this gameplay test. It ends by starting revision-two Emberwatch with all eight buildings.

The separate result-boundary tests deliberately set the enemy citadel to zero to isolate transition/reward behavior. They are labeled in source and are **not** evidence of a winning strategy. The paid gameplay test is the completion evidence.

## Defect caught during integration

The first actual restricted field-guide call threw because the catalogue eagerly constructed siege, wizard, mine and tower copy even when those definitions were absent. This prevented the fresh title briefing/start path from functioning. Runtime now constructs only available role/structure entries. The new tests call the real field-guide implementation, rather than leaving the startup fixture's no-op catalogue in place, so this regression is covered.

The focused suite passed 95 tests on the integration candidate. The aggregate Node suite then passed 920 tests, with zero failures and one pre-existing skipped test (about 40.5 seconds). Re-run aggregate checks after any later runtime edit; a focused pass is not a complete release gate.

## Explicit limits

This is Node/VM integration and real engine gameplay evidence. It does not run a browser, load CSS, exercise native touch/pointer events, inspect rendered pixels, verify portrait drawing or prove accessibility/focus actionability. `innerHTML` is retained as generated markup rather than parsed into a browser DOM. The backup bridge removes only Node VM prototype differences before calling the real codec. Download creation is captured as text, not an operating-system download.

Native browser/mobile playthrough, screenshots, target size/clipping, orientation transitions, visual hierarchy and final packaged/offline checks remain separate required gates. No server, browser, release publish, external upload or PR action was started for this test work.


## Browser regression preparation

Six current-path tests were added in `qa/browser/campaign-progression.spec.mjs`:

- Fresh title, locked mission, two-card roster, catalogue and absent expansion bypass.
- All three paid last-active checkpoints complete through real browser ticks in one profile; each real result is persisted, Continue starts the next roster, and reload keeps the earned records. The final launch is revision-two Emberwatch with its Warden lodge.
- A saved two-card battle is resumed against newer eight-building progress. Its two-star result has no newly earned reward, while explicit replay has eight cards.
- Revision-two Emberwatch accepts a paid Warden lodge and retains the battle identity and formation through reload and backup import.
- Intro-only records remain visible without skipping the new opening; returning main progress retains all eight buildings.
- Unknown campaign progress refuses ordinary export without a download or any replacement of the original bytes.

`campaign-progression-fixtures.mjs` generates active checkpoints by paid builds/upgrades and real combat. `validate-campaign-progression-fixtures.mjs` verifies independent save admission, exact restore, backup roundtrip and next-tick completion. The three paid final active checkpoints are approximately 60.45, 114.40 and 113.35 seconds. A separate paid two-star Roadside Watch route supplies the replay case. The 30-second checkpoints are also validated. Initial prerequisite profiles used for standalone cases are explicitly labeled fixtures; the sequential browser case preserves progress earned by earlier browser results rather than inserting later completion records.

Existing browser changes are narrowly scoped:

- `campaign-onboarding.spec.mjs`: current fresh defaults/save identity and two-card resume; an explicit revision-one saved lesson retains the old seven-card expansion regression.
- `integrated-flow.spec.mjs`: explicit legacy lesson selection, preserved intro records and the new intro-only default/Continue destination.
- `campaign.spec.mjs`: declared earned-opening profile for fresh main launches; an explicitly seeded revision-one battle preserves version-two save/reload coverage; legacy saved victory/deadline/retry assertions remain legacy.
- `expanded-campaign.spec.mjs`: fresh current launches assert revision two, eight buildings and unchanged authored formations. Existing revision-one success/failure/retry/backup fixtures remain unchanged. Returning profile bytes and named old records are still checked exactly, with no invented new-lesson records.
- `accessibility-backup.spec.mjs`, `profile-upgrade.spec.mjs` and `production-upgrade.spec.mjs`: exact current UI totals and protocol-four migration expectations. Original old-client/engine/save identities and byte-for-byte preservation checks remain intact. The future marker is now protocol five.
- `storage-recovery.spec.mjs` and `regression.spec.mjs`: only three current-profile ready-marker assertions changed from protocol three to four; save/engine version-three assertions were not changed.

Validated without launching a browser:

The existing browser static/fixture check passed. The new validator is a separate command because this work did not change package scripts. The six new tests are authored for the existing four Playwright projects (24 configured executions). They and the modified browser tests **have not been executed in a browser here**. This environment has no installed local `@playwright/test`; the authorized browser runner must discover and run them. No browser/server startup was attempted.
